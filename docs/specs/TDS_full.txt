SAARTechnical Design Specification v1.0
Implementation blueprint: architecture → database → APIs → events → AI → security → CI/CD
Co-founder: Sujal Kumar  |  Strategic / Technical M.D.: GPT  |  Status: Draft for implementation
1. Purpose
This specification converts the SAAR Product Requirements Document into an implementation-level technical blueprint. ""It is intentionally opinionated: the first release should be modular, secure, observable, testable and capable of evolving from an MVP into a multi-region consumer product without rewriting its core domain model.
Primary product loop:
Current You → Desired You → Gap → Action → Behavior → Evidence → Insight → Adaptation → Repeat.
SAAR is not a generic task manager. The technical architecture must preserve longitudinal behavioral context and turn it into explainable, bounded interventions.
AI is an orchestration layer over trusted application data—not the source of truth.
2. Architecture Principles
Modular monolith first: keep domain boundaries strict while avoiding premature microservice complexity.
API-first: mobile/web clients consume stable versioned contracts.
PostgreSQL is the system of record; Redis is acceleration/state, never authoritative business storage.
Event-driven side effects: reminders, analytics, AI analysis and weekly reports are asynchronous.
AI never mutates critical user state directly. It proposes actions; policy + domain services validate and commit them.
Privacy by design: collect the minimum data necessary, make sensitive features opt-in, support export/delete.
Every important behavioral event is timestamped and attributable to a device/session/source.
Observability is a feature: every workflow must be diagnosable with correlation IDs.
Feature flags protect risky releases and permit controlled experiments.

9. Authentication & Authorization
Use short-lived access tokens and rotating refresh tokens stored in secure platform storage.
Device/session records enable revocation and anomaly detection.
Authorization must be server-side on every protected resource.
Use RBAC internally (user/admin/support) but keep domain ownership checks mandatory.
Prepare for passkeys and MFA; do not hard-code password-only assumptions.
Never trust client-provided user_id, role, organization_id or ownership fields.
Rate-limit login, OTP, password reset, companion messaging and expensive AI endpoints.
Sensitive operations require step-up authentication when appropriate.
10. AI Architecture
The AI layer is a controlled decision-support system with four stages:
Context Builder: retrieves only the minimum approved context needed for the task.
Policy Engine: checks permissions, safety, privacy, age/eligibility and tool constraints.
Model Router: selects model/provider based on task complexity, latency and cost.
Action Validator: converts AI output into a strict schema and allows only whitelisted mutations.
AI tools should be explicit, typed and permission-scoped, for example:
get_today_plan()get_recent_behavior(days)get_goal_progress(goal_id)get_balance_snapshot()create_task(proposed_task)          # requires user confirmation for sensitive changesreschedule_task(task_id, new_time)  # policy checkedcreate_insight(insight_payload)save_memory(memory_payload)         # explicit memory policy / consent
Do not expose a generic SQL tool or unrestricted application database to the model.

12. Life Trade-off Engine
SAAR must treat time and attention as constrained resources. A recommendation that improves one life area while repeatedly damaging another is not automatically a good recommendation.
Represent daily capacity as available time blocks rather than assuming unlimited availability.
Maintain life-area weights selected by the user.
Detect overload: planned effort > estimated capacity.
Detect displacement: adding work consistently removes sleep, exercise, relationships or personal time.
Recommend trade-offs explicitly: reduce, move, delegate, defer or drop.
Never optimize a single score at the expense of the user's stated values.
13. Adaptive Scheduling
Store intended time and actual completion time.
Calculate success rates by time window, day-of-week, context and task type.
Require a minimum evidence threshold before moving a recurring routine automatically.
Propose changes first; optionally enable auto-rescheduling for low-risk routines.
Respect fixed commitments and user-defined no-move windows.
Every adaptation is logged so the user can understand why the schedule changed.
14. Daily Growth Session
Trigger: user's configured local time1. Lock daily snapshot2. Collect plan + completed/failed behavior3. Run feature aggregation4. Calculate goal/gap changes5. Generate 3–5 concise insights6. Ask mood/energy/reflection questions7. Recommend tomorrow's top actions8. Save session summary9. Schedule next-day reminders10. Record outcome events
Performance target: render the session quickly from precomputed aggregates; never wait for a full LLM analysis before showing basic progress.
15. Companion Conversation Flow
User message enters API → authentication → rate limit → safety classifier → context selection.
Context Builder retrieves relevant recent conversation, goals, behavior summaries and user-approved memories.
Prompt is assembled from versioned templates.
Model returns structured response plus optional action proposals.
Schema validator rejects malformed tool/action outputs.
Policy layer decides whether confirmation is required.
Response is stored with a redacted/structured audit record where appropriate.
Sensitive raw conversation should not automatically enter analytics or long-term memory.

17. Notification / Alarm System
Notification scheduling service stores intended notifications and delivery state.
Client handles platform-specific local alarm behavior where OS capabilities are stronger.
Server remains authoritative for schedule and recurring rules.
Alarm dismissal actions are modeled as events.
Behavioral alarms may require a configurable action (e.g., scan/step/task), but provide accessibility and emergency bypasses.
Never use coercive or unsafe mechanics. The goal is accountability, not punishment.
18. Event-Driven Processing
Transactional request   ↓DB transaction   ├─ write business state   └─ write outbox event          ↓Outbox publisher          ↓Queue   ├─ analytics worker   ├─ notification worker   ├─ growth feature worker   └─ AI insight worker
Use the transactional outbox pattern so important domain changes are not committed without their corresponding event.
19. Idempotency & Reliability
All write endpoints that may be retried accept an idempotency key.
Workers must be safe to retry.
Use exponential backoff and dead-letter queues for persistent failures.
Every job has status, attempts, started_at, finished_at and error metadata.
External provider calls use timeouts and circuit-breaking where appropriate.
User-visible operations should return a correlation ID for support/debugging.
20. Security Architecture
TLS everywhere; HSTS on web.
Secrets only in managed secret storage/environment configuration; never commit secrets.
Encrypt data at rest using platform/database/object-store encryption.
Signed, short-lived object URLs for private files.
Strict CORS and CSRF strategy based on auth mechanism.
Content validation and malware scanning for uploads.
PII/sensitive-content classification at schema level.
Audit logs for authentication, privacy actions, role changes and critical account changes.
Dependency scanning, secret scanning, SAST and container scanning in CI.
Threat-model high-risk flows before launch.
21. Privacy & Data Lifecycle
Explicitly explain why each sensitive permission/data source is requested.
Default to minimal collection.
Allow users to disable optional integrations.
Provide export and deletion workflows.
Separate operational data from product analytics where possible.
Define retention periods per data class.
Use data minimization in AI context retrieval.
Never sell or share personal growth data as a default business model.

28. Billing / Monetization Architecture
Separate entitlement state from payment provider implementation.
Maintain subscription, plan, entitlement and provider-event tables.
Use provider webhooks as the source of truth for payment state.
Gate premium capabilities server-side.
Support grace periods and failed-payment states.
Do not make safety-critical or basic privacy controls paywalled.
29. Feature Flag Architecture
Flags are server-evaluated for entitlement/security-sensitive behavior.
Support user cohort, percentage rollout and environment targeting.
Every flag has owner, purpose, created date and expiry date.
Remove stale flags; do not accumulate permanent branches.

35. Claude Code / Antigravity Execution Contract
Agents should implement one bounded phase at a time. They must inspect the existing repository before changing architecture, preserve working behavior, write tests for critical paths, update documentation, and never silently introduce infrastructure or dependency choices.
For every implementation task:1. Inspect current repository and identify affected modules.2. State assumptions and risks.3. Produce a short implementation plan.4. Implement in small reviewable commits.5. Add/update tests.6. Run lint, typecheck, unit/integration tests.7. Check authorization and failure paths.8. Update API/schema/docs.9. Report files changed, migrations, env vars and rollback steps.10. Do NOT modify unrelated modules.

37. Final Technical Contract
SAAR v1 should be built as a privacy-first, modular, event-aware application whose source of truth is deterministic application data and whose AI layer is bounded, explainable and replaceable. ""The architecture deliberately optimizes for a solo/small engineering team: strong module boundaries, one deployable backend initially, PostgreSQL as the durable core, Redis for acceleration, asynchronous workers for expensive work, and strict CI/CD. ""The product's technical moat is not the chat model; it is the longitudinal behavioral model, the gap engine, adaptive interventions and trusted user-controlled memory.
