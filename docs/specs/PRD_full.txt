PRD v1.0 • Founding Product Specification • India-first
Owner: Sujal Kumar, Co-founder | Strategic/Technical M.D.: GPT
Document purpose: convert the SAAR founding thesis into an implementation-ready product contract covering product behavior, workflows, data flows, pipelines, architecture boundaries, MVP scope, safety, privacy, metrics, and go-to-market readiness.
1. Executive Summary
SAAR is an India-first Personal Growth Intelligence product. It is not positioned as a conventional habit tracker, task manager, meditation app, or generic AI assistant. Its core job is to continuously compare a user's Current Self with their Future Self, identify meaningful gaps, understand behavioral causes, recommend a small number of interventions, observe outcomes, and adapt.
The core loop is: Future Self → Current Self → Measure → Find Gap → Understand → Recommend → Act → Observe → Learn → Adapt.
The MVP must prove one hypothesis: SAAR can help real users make measurable positive changes in their behavior over 30 days. Downloads, streaks, time spent in app, and AI message volume are secondary.
Product promise
Know how you live. Understand where you're going. Become who you want to be.
Category
Personal Growth Intelligence
Primary market
India, initially focused on digitally active Gen Z and young adults roughly 18–30; the product architecture should not hard-code this age segment so it can expand later.

3. User Problem
Users know what they want but struggle to translate intentions into consistent behavior.
Planning, fitness, journaling, calendars, habits, and AI conversations are fragmented.
Most tools record completion but do not explain why patterns occur.
Rigid plans fail when real life changes.
Productivity systems can unintentionally encourage overwork.
Users lack a longitudinal model of how their behavior affects their goals.

5. Jobs To Be Done
When I know what I want to improve but keep failing to act consistently, help me understand why and change the plan.
When my day becomes chaotic, help me decide what actually matters.
When I repeatedly miss a habit, help me distinguish motivation problems from schedule/design problems.
When I feel overwhelmed, help me see the trade-offs instead of adding more tasks.
When I reflect on my week, show me what actually changed and what pattern caused it.
When I talk to the AI, use my context responsibly instead of giving generic advice.

Email/password and a supported social sign-in provider.

Short-lived access tokens and revocable sessions.
Secure device storage for tokens on mobile.
Account recovery and device/session management.

9.2 Future Self
Create/update aspirations by domain.
Define 1–3 priority goals during onboarding.
Allow goals to be measurable or behavior-based.
Allow users to pause, archive, or replace goals.
Never force every life domain.
9.3 Goals
Goal title, domain, reason/why, target date, priority, measurement method, status.
Goal-to-habit/task relationships.
Goal progress snapshots.
Goal history must remain auditable for AI reasoning.
9.4 Tasks / Schedule
One-time and recurring tasks.
Flexible rescheduling.
Completion, skip, snooze, cancel, reschedule events.
Calendar-style view.
Conflict detection.
Time-budget awareness.
9.5 Habits
Frequency, preferred time window, minimum viable action, target, tracking mode.
Track completion and misses.
Distinguish skipped, failed, rescheduled, and completed.
Support habit experiments rather than permanent streak pressure.
9.6 Behavioral Alarm
User chooses an intervention type.
Alarm creates a behavior event when triggered.
Dismissal may require an action such as confirmation, movement, QR/NFC, or micro-task depending on device capabilities.
Do not use dangerous or punitive interventions.
Repeated failure triggers adaptation analysis rather than escalating punishment.
9.7 Check-in
Mood: lightweight categorical scale.
Energy: simple numeric scale.
Optional free-text reflection.
User controls whether check-ins are required.
9.8 SAAR Daily
Triggered at user-selected local time.
Collects relevant day events.
Asks a minimal check-in.
Computes key deviations from plan.
Generates up to three high-value insights/actions.
Offers tomorrow plan adjustment.
9.9 Weekly Growth Review
Compare current week with prior baseline.
Highlight improvements and declines.
Show meaningful patterns with supporting evidence.
Propose 1–3 changes for the next week.
Allow user feedback on whether an insight was useful.

14. Workflows
14.1 Onboarding
Acceptance criteria
User can reach a first meaningful plan in one session.
User understands why SAAR asks about Future Self.
Privacy permissions are explicit and granular.
At least one goal and one actionable item exist after activation.
14.2 Daily Growth Session
Acceptance criteria
Session can be completed in approximately 3–7 minutes.
Insights cite relevant evidence.
No more than three primary recommendations are shown by default.
User can dismiss, accept, edit, or postpone recommendations.
14.3 Behavioral Alarm
Schedule → Trigger → Intervention → User action → Completion/Failure event → Outcome analysis → Adaptation suggestion.
14.4 Recommendation lifecycle
Signal detected → eligibility rules → context retrieval → deterministic checks → AI interpretation if needed → safety/policy filter → recommendation → user decision → outcome tracking → effectiveness score.
14.5 Account deletion
Request deletion → re-authenticate → show deletion scope → grace period if legally/operationally appropriate → revoke sessions → delete/anonymize data by retention policy → delete AI memory/indexes → confirm completion.
14.6 Safety escalation
Risk signal → safety classifier/rules → restrict unsafe coaching behavior → supportive response → encourage appropriate human/professional help where relevant → record minimal safety event → protect access to sensitive data.

17. AI / Data Pipeline
Pipeline rules
Raw events are immutable where practical and are never directly trusted as AI instructions.
Normalize timestamps to a canonical server format while preserving user timezone.
Separate factual user data from inferred insights.
Attach provenance to insights: source events, time window, model/rule version.
Do not write an AI inference into durable memory without an explicit confidence/validation policy.
Run safety and privacy filtering before user delivery.
18. Notification Pipeline
Scheduled event → notification eligibility → quiet hours / user preference check → relevance check → deduplication → delivery provider → delivery result → interaction event → effectiveness analysis.
Respect local timezone.
Respect quiet hours.
Prevent notification storms.
Allow per-category controls.
Use notification outcome as a behavioral signal only with appropriate privacy controls.
19. CI/CD Pipeline
Developers work on feature branches.
Pull requests require automated quality gates.
Main is protected.
Production deployments require successful CI and explicit approval during early stages.
Secrets are injected through environment/secret management, never committed.
Database migrations are versioned and reversible where feasible.
Production releases must be observable and rollback-ready.

21. Security & Privacy Requirements
Server-side authentication and authorization; never trust client-side role/permission checks.
HTTPS/TLS for all network communication.
Secure mobile token storage using platform mechanisms.
No secrets, passwords, API keys, or sensitive journal text in logs.
Least-privilege access to sensitive data.
Data retention and deletion policies must be explicit.
Audit access to highly sensitive administrative operations.
Rate-limit authentication, AI, and abuse-prone endpoints.
Threat-model the mobile/web/API/AI boundaries before public launch.
OWASP's current mobile guidance explicitly recommends secure-by-design architecture, server-side authorization, secure token handling, HTTPS, least privilege, and protection against sensitive-data leakage. citeturn0search6turn0search9

33. Definition of Done — MVP
A new user can sign up and create a Future Self.
User can create goals and actionable tasks.
User can schedule and receive reminders.
User can complete/skip/reschedule actions.
Behavioral alarm can trigger at least one safe intervention type.
Daily session summarizes the day using real product data.
AI can answer contextual questions using authorized data.
Gap Engine can produce at least one evidence-backed insight.
Weekly Review compares current behavior with a baseline.
User can export/delete their data through supported flows.
All protected APIs enforce authorization server-side.
Sensitive data is not emitted into normal application logs.
CI passes lint/typecheck/tests/security checks before deployment.
Observability exists for API, jobs, notifications, and AI failures.

35. Final Product Contract
SAAR is successful only if it creates value in the user's real life. The product team must resist the temptation to measure success by AI message volume, screen time, streak length, or feature count. Every major product decision should answer one question: does this make SAAR better at helping the user understand their behavior and make a meaningful improvement?
This PRD is the product contract for the next technical design stage. Architecture, schemas, API contracts, UX specifications, event taxonomy, AI evaluation, security controls, and implementation tickets should be derived from it rather than invented independently.
