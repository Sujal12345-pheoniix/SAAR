1. Contract Purpose
This document freezes the first implementation contract between SAAR clients, backend modules, database and asynchronous workers. It is designed to prevent agents from inventing inconsistent schemas or endpoints while development proceeds in parallel.
PostgreSQL is authoritative for transactional state.
REST /api/v1 is the initial external contract.
All IDs are UUIDv7/time-sortable UUIDs.
All timestamps are stored in UTC.
Client-visible timestamps are converted to the user's configured timezone.
Every resource is tenantless in v1 but always user-owned; organization support can be introduced later without rewriting ownership semantics.
Sensitive AI/conversation content is deliberately excluded from product analytics events.

4. API Standards
Base URL: /api/v1.
Content-Type: application/json.
Request ID: X-Request-Id; server generates one if absent.
Idempotency-Key required for retry-prone POST mutations.
Authorization: Bearer access token.
Pagination: cursor-based for timelines; limit capped server-side.
Dates: ISO-8601 UTC; date-only fields explicitly documented as local dates.
Never return password hashes, refresh token hashes, internal provider credentials or raw security metadata.

20. Seed Data Contract
Seed only development/test data:- demo user- six life areas- three sample goals- seven sample tasks- sample routine- synthetic behavior events- sample insight- sample daily check-inNever seed real email addresses, credentials, tokens or production-like personal data.
21. Database Migration Rules
Every schema change is a migration committed to source control.
Backward-compatible changes first when mobile clients may lag behind backend deployment.
Destructive changes require a separate migration and explicit rollback/backup plan.
Never edit an already-applied production migration.
Use migration checks in CI against a clean database.
Production migrations run through deployment automation with lock/timeout safeguards.
22. Pagination / Filtering Contract
GET /tasks?status=TODO&limit=50&cursor=<opaque>{  "data":[...],  "page":{    "nextCursor":"...",    "hasMore":true  }}
Default limit: 20.
Maximum limit: 100.
Cursor values are opaque.
Sort order is deterministic.
Do not use offset pagination for large behavioral timelines.
23. Validation Rules
All request bodies validated server-side with typed DTO schemas.
Unknown fields rejected for security-sensitive endpoints.
String lengths, numeric ranges, enum values and date ranges validated.
Goal/task titles normalized for whitespace but original user meaning preserved.
Reflection and conversation content are treated as sensitive text.
Timezone must be a valid IANA timezone.
24. Idempotency Contract
Header:Idempotency-Key: <client-generated unique value>Server:1. hash normalized request2. store key + user + endpoint + response status/body3. return same response for safe retries4. reject same key with different request body5. expire keys after defined retention window
25. API Security Checklist
Authentication on every protected route.
Authorization + ownership check on every resource route.
Rate limits per user/device/IP where appropriate.
Request body size limits.
Output filtering for sensitive fields.
Audit critical mutations.
CSRF protection where cookie-based auth is used.
Strict CORS.
Secure headers.
Dependency and secret scanning in CI.

27. Contract Testing Requirements
Every endpoint has success, validation, authentication and authorization tests.
Every mutation has an idempotency/retry test where applicable.
Every resource route has owner vs non-owner test.
OpenAPI contract is generated/updated from DTO definitions.
Mobile client must consume generated types rather than duplicate API interfaces.
Breaking API changes require a version bump or compatibility layer.
28. What Claude Code Must NOT Do
Do not replace PostgreSQL with localStorage for real user state.
Do not create a second source of truth for goals/tasks.
Do not expose Prisma/database access directly to controllers.
Do not allow the LLM to call arbitrary SQL.
Do not store secrets in source control.
Do not bypass authorization because the UI hides a button.
Do not create microservices merely to make the architecture look enterprise.
Do not introduce a new dependency without explaining why it is necessary.
Do not modify unrelated modules while implementing a phase.
29. Phase 0 Acceptance Criteria
Repository builds from a clean checkout.
Local PostgreSQL migration succeeds.
API health and readiness endpoints work.
Auth flow works from a fresh database.
Session revocation works.
Profile persists across devices/sessions.
CI runs lint/typecheck/tests.
Secrets are externalized.
Request correlation appears in logs.
Unauthorized resource access returns 403/404 according to policy.
Initial OpenAPI contract is generated and versioned.
30. Final Contract
This pack is the implementation contract for SAAR's first engineering cycle. The schema and API boundaries intentionally favor correctness, ownership enforcement, observability and future evolution over premature complexity. Claude Code and Antigravity should treat this document together with the Technical Design Specification and PRD as the authoritative baseline; any deviation should be recorded as an ADR before implementation.
